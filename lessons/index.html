AgentOps, explained one idea at a time

Thirty-three short lessons that walk through the AgentOps project — the router, the durable tracker, the fact-checker, the traces, the MCP server, and the v1.0 gateway and console — and the engineering decisions behind them. Each lesson is one idea, in plain words, with the real code, a thing to try, and the questions an interviewer would ask.

Read them in order the first time. Each one takes about five minutes.

Part 1 · Big picture

  • 01What AgentOps is, in one breathAgentOps is four small tools that make running AI models safer: a traffic cop, a task tracker, a fact-checker, and a dashboard.
  • 02Why it exists, and the constraints that shaped itThe goal is a finished, demoable, own-code project for a CV — built solo, on one RTX 4060 with 8 GB of VRAM.
  • 03The repo layoutOne monorepo, one go.mod, five packages — each package is one of the tools.
  • 04One binary, many modesThe same executable is a web server, an MCP server, a migration tool, an eval runner and a workflow runner — chosen by a command-line flag.
  • 05Configuration from environment variablesAll settings come from env vars with sensible defaults, read once at startup into a Config struct.

Part 2 · The router

  • 06Talking to a local LLM: the Ollama clientOllama runs models on your GPU and exposes a plain HTTP API; the router calls POST /api/generate with the standard library.
  • 07The routing rule (the 'traffic cop')A prompt goes to the fast 3B model unless it is longer than 200 characters or contains a 'complex' keyword — then it goes to the quality 7B model.
  • 08The HTTP server and one error shapeA standard-library net/http server with three routes and exactly one JSON error format.
  • 09Interfaces and fakes: how the tests stay fastThe router depends on a one-method Generator interface, so tests swap in a fake instead of a real model.
  • 10Prometheus metrics, written by handThe router counts requests, errors and tokens per model and keeps a latency histogram, then prints them in Prometheus text format at GET /metrics.
  • 11Seeing the numbers: Grafana dashboard and k6 load testA Grafana dashboard stored as JSON draws the router's metrics in five panels, and a k6 script measures the router's own overhead at 50 requests/second.

Part 3 · MCP control surface

  • 12MCP: letting an AI assistant call your serverMCP (Model Context Protocol) is JSON-RPC 2.0 over stdin/stdout; an AI client like Claude Desktop launches your binary and calls its 'tools'.
  • 13The five MCP toolslist_models, get_stats, route_test_request, inspect_trace, get_drift_report — each one is a thin wrapper over something the router already does.

Part 4 · The fact-checker (RAG + evals)

  • 14RAG in plain wordsRAG = find the relevant text first, then let the model answer using only that text. Retrieval-Augmented Generation.
  • 15The corpus cleaner: chunking and dedupA 90-line Python script turns markdown docs into clean, overlapping, de-duplicated chunks — and running it twice gives the same result.
  • 16pgvector and HNSW: vector search inside PostgresInstead of a separate vector database, the chunks and their 768-number embeddings live in Postgres with the pgvector extension and an HNSW index.
  • 17The database schema and migrationsSeven tables in two SQL files, applied in filename order by a 20-line Go function.
  • 18The golden set: draft with a model, review by handA golden set is a list of question/answer pairs you know are correct; a model drafts them from your docs, then a human reviews every single one.
  • 19The faithfulness scorer: split claims, judge each oneFaithfulness = the fraction of an answer's sentences that a judge model says are supported by the retrieved text.
  • 20Retrieval precision and recallPrecision@k = of the k chunks we fetched, how many came from the right document. Recall@k = of the right documents, how many did we fetch.
  • 21LLM-as-judge: bias guards and prompt versioningWhen a model grades another model, you must guard against its known biases and record exactly which judge and which prompt produced every score.
  • 22Retry with backoff — and when NOT to retryJudge calls retry with exponential backoff and jitter, honour Retry-After on 429, and never retry a 4xx that is the caller's fault.
  • 23Drift detection: did the score drop?Every eval run is stored; the drift report compares the last two runs for a golden version and alerts when the latest score is below the threshold.
  • 24The scheduler is a flag, not a service--schedule-evals 24h runs the exact same scoring function in a loop, forever, and logs loudly if one tick fails.

Part 5 · The durable task tracker

  • 25Durable execution: workflows that survive crashesEach step of a multi-step task writes its status to Postgres before and after running, so a restarted process can see where it was and continue instead of starting over.
  • 26The kill -9 testThe proof of durability is a test where step 2 fails, the workflow is re-run with the same id, and step 1 is not executed again.

Part 6 · Traces and observability

  • 27Tracing: trace_id, span_id, parent_idA trace is the story of one request; a span is one step in it. Every span carries trace_id (which story), span_id (which step) and parent_id (which step came before).
  • 28The async span writer: never slow a request for telemetryRouter spans are pushed onto a buffered channel and written to Postgres by one background goroutine; a dead database costs the chat request nothing.

Part 7 · Engineering process

  • 29What a deep review found (and why each bug mattered)After the code was 'done', every file was re-read against a checklist; 15 findings came out, 14 were fixed the same day with a binding test each — then three more surfaced while writing these lessons and running the first full golden suite.
  • 30How to tell this story in an interviewPitch it as: 'I built a focused, from-scratch version of the AgentOps pattern — router, durable tracker, evals, traces — in Go, informed by how TensorZero, Bifrost, Temporal and Langfuse solve the same problems.'

Part 8 · v1.0 product

  • 31From router to gateway: OpenAI shape, streaming, backendsv1.0 made the router something a real client can point at: OpenAI-compatible messages[] in and out, SSE streaming, and pluggable backends (Ollama + any OpenAI-style cloud API) behind one Backend interface.
  • 32Virtual API keys and the fail-closed ruleCallers get virtual keys with a per-minute limit and a lifetime token budget; and a request flagged sensitive never reaches a cloud backend — even when every local model is down.
  • 33The Tower console: a UI with no framework and no buildThree static files embedded in the binary — HTML, CSS on the Tower design tokens, and a small JS hash router — read a handful of JSON endpoints and show overview, traces, evals and workflows.
