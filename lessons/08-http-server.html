Part 2 · The router

The HTTP server and one error shape

In one sentence

A standard-library net/http server — four routes in the router package, a few more mounted by main.go — and exactly one JSON error format.

Why it exists

No web framework. Go 1.22+ routing patterns ("POST /v1/chat/completions") make the stdlib enough. One error shape means every client — curl, Grafana, Claude via MCP — can parse failures the same way.

How it works in this project

// router/server.go
func NewServer(fastModel, qualityModel string, local Backend) *Server {
    s := &Server{…, Metrics: NewMetrics(), Limiter: NewRateLimiter(), RequestTimeout: 300 * time.Second}
    s.mux = http.NewServeMux()                          // built ONCE (deep-review fix #3)
    s.mux.HandleFunc("POST /v1/chat/completions", s.handleChat)   // auth → parse → plan → backend (or SSE)
    s.mux.HandleFunc("GET /v1/models", s.handleModels)
    s.mux.HandleFunc("GET /health", s.handleHealth)
    s.mux.HandleFunc("GET /metrics", s.handleMetrics)
    return s
}
// main.go mounts on top: GET /v1/traces/{id}, GET /v1/drift/report, and the console's / and /v1/{overview,requests,evals,workflows}

type ErrorBody struct{ Error ErrorDetail `json:"error"` }
type ErrorDetail struct {
    Code    string `json:"code"`      // "bad_request", "ollama_unavailable", "trace_not_found"
    Message string `json:"message"`
    TraceID string `json:"trace_id"`  // so a user can quote it and you can find the trace
}

Status codes are deliberate: 400 missing prompt, 502 Ollama down (it's an upstream failure, not ours), 404 unknown trace id. In main.go two more routes are added on top: GET /v1/traces/{id} and GET /v1/drift/report.

Try it yourself

curl -i localhost:8080/v1/chat/completions -d '{}'
# HTTP/1.1 400 ... {"error":{"code":"bad_request","message":"prompt is required","trace_id":"…"}}

Interview questions

Q Why 502 and not 500 when Ollama is down?
A 502 Bad Gateway means 'the thing behind me failed'. That's precisely what happened, and it tells an operator where to look.
Q What was the ServeMux bug?
A The first version built a new ServeMux inside ServeHTTP — on every request. It worked but allocated and re-registered routes per call. Deep-review caught it; now it's built once in NewServer.
Q Why put trace_id in errors?
A So a failing request is debuggable. The user pastes the id, I run go run . --trace <id> and see what happened.

Remember

  • stdlib net/http, no framework; router routes + main.go routes on one mux.
  • One error shape: {error:{code,message,trace_id}} — 400/401/403/404/429/502/504 all use it.
  • Build the mux once.
