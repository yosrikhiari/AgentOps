The database schema and migrations

In one sentence

Nine tables in three SQL files, applied in filename order — once each — by a 40-line Go function that records what it ran.

Why it exists

Schema in versioned SQL files is the simplest migration system that works. Every table maps to one tool, so the schema is also a map of the project.

How it works in this project

docs / chunks               ← RAG corpus (evals)
workflows / steps           ← durable tracker
spans                       ← traces (router AND tracker write here)
eval_runs / eval_pair_scores← eval history for drift (0002_drift.sql)
api_keys                    ← virtual keys, hash only (0003_api_keys.sql, v1.0)
schema_migrations           ← which files above have been applied (v1.0)

-- evals/corpus.go
func Migrate(ctx, db Execer, q Queryer, dir string) (applied int, err error) {
    db.Exec(ctx, "CREATE TABLE IF NOT EXISTS schema_migrations (filename TEXT PRIMARY KEY, applied_at …)")
    done := rows of SELECT filename FROM schema_migrations
    for _, f := range sorted(*.sql) {          // 0001_ before 0002_ before 0003_
        if done[f] { continue }                // applied once, ever
        db.Exec(ctx, readFile(f)); db.Exec(ctx, "INSERT INTO schema_migrations …", f); applied++
    }
}

The MVP version had no tracking table and relied on every statement being CREATE … IF NOT EXISTS — fine while migrations are additive, unsafe the day one needs ALTER. v1.0 Track A added schema_migrations: each file is recorded when applied and skipped afterwards (TestMigrateSkipsApplied); live, --migrate reports applied 2 then applied 0. Migration 0003 (API keys) was the first one written under the new rule.

Key indexes: (workflow_id, seq) primary key on steps, spans(trace_id), eval_runs(golden_version, created_at DESC) for 'last two runs' queries.

Try it yourself

cat migrations/0001_init.sql and find the one ON DELETE CASCADE in 0002_drift.sql: deleting an eval run removes its per-question scores.

Interview questions

Q Why two migration files?
A 0001 was the MVP schema. 0002 added eval_pair_scores when drift reporting needed per-question scores (ADR-0005). You never edit an applied migration; you add a new one.
Q How do you know a migration won't run twice?
A A schema_migrations row per applied file; the runner skips anything listed and returns how many it applied. The first version had no table and leaned on IF NOT EXISTS — I replaced that before writing the first non-additive migration.
Q Why is spans keyed on (trace_id, span_id)?
A A span is unique within its trace. The composite key plus ON CONFLICT DO NOTHING makes span writes idempotent — retrying a write can't duplicate.

Remember

  • 9 tables, 3 SQL files, applied once each (schema_migrations).
  • Never edit an applied migration; add a new one.
  • spans keyed on (trace_id, span_id) → idempotent writes.
