The async span writer: never slow a request for telemetry

In one sentence

Router spans are pushed onto a buffered channel and written to Postgres by one background goroutine; a dead database costs the chat request nothing.

Why it exists

The first version opened a fresh Postgres connection per span, synchronously, three times per chat, with a 2 s timeout — so a down database added 6 s to every chat. Telemetry must never be on the request's critical path.

How it works in this project

// main.go
type spanWriter struct {
    db      pgDB
    queue   chan spanRecord          // 1024 deep
    dropped atomic.Uint64
}
func newSpanWriter(db pgDB) *spanWriter { w := ...; go w.loop(); return w }

func (w *spanWriter) loop() {               // ONE goroutine, in emit order
    for rec := range w.queue {
        ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
        _, err := w.db.Exec(ctx, `INSERT INTO spans ... ON CONFLICT DO NOTHING`, ...)
        cancel()
        if err != nil && w.dropped.Add(1) == 1 { log.Printf("span sink: first write failure ...") }
    }
}
func (w *spanWriter) Sink() router.SpanSink {
    return func(traceID, spanID, parentID, name, attrs string) {
        select {
        case w.queue <- spanRecord{...}:     // request path cost: one channel send
        default: w.dropped.Add(1)           // queue full → drop, count, don't block
        }
    }
}

The router itself only knows a SpanSink function type; in tests it's a slice-appending closure, in production it's this writer. The pgx pool (not a per-call connection) is shared by spans, traces and drift queries.

Try it yourself

Stop Postgres (docker compose stop) and send a chat. It still returns in model-time; the log shows one 'span sink: first write failure' line, not one per span.

Interview questions

Q How do you keep observability from hurting latency?
A Buffer it. Producers do a non-blocking channel send; one consumer goroutine does the I/O. Full buffer → drop and count. Never block the request.
Q Why one goroutine and not one per span?
A Ordering (spans arrive in emit order) and bounded concurrency (one DB writer, not thousands). A single ordered worker is the simplest correct design here.
Q Why log only the first failure?
A A down database would otherwise print thousands of identical lines. First failure + a dropped counter is enough to diagnose without flooding.

Remember

  • Non-blocking send on the request path.
  • One ordered goroutine writes to the pool.
  • Drop + count when full; log first failure once.
