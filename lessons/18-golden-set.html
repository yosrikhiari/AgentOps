The golden set: draft with a model, review by hand

In one sentence

A golden set is a list of question/answer pairs you know are correct; a model drafts them from your docs, then a human reviews every single one.

Why it exists

Every eval score is measured against the golden set. If a golden answer is wrong, every score after it is wrong and nobody notices. This is the one step that cannot be automated away.

How it works in this project

// evals/synthesizer.go — the draft prompt, per chunk
Write exactly 2 factual question-answer pairs answerable ONLY from the passage below.
Rules: answers use only passage facts, questions are specific, no preamble,
output a raw JSON array, nothing else.

// evals/golden/v1_draft.jsonl — one JSON object per line
{"question":"What determines which model a chat request is routed to?",
 "answer":"A heuristic classifier that routes short simple prompts (200 characters or fewer ...",
 "doc_ids":["01-router"]}

The workflow (issue #5 in the plan):

  • go run . --draft-golden → 32 pairs in v1_draft.jsonl (local model, 2 per chunk).
  • Human reads all 32 against the source docs, fixes or deletes bad ones, saves as v1.jsonl.
  • go run . --freeze-golden validates (no empty fields, no unknown doc ids, no duplicate questions) and writes v1.sha256.
  • Any doc change → bump to v2. The hash proves which set a score was measured against.

Status: v1 frozen (32 pairs, 29dd81c5…, faith 0.969) and v2 frozen the same day (48 pairs, 8882c136…) after the corpus was rewritten to match the shipped code — every v2 answer is a full sentence by rule. v2 scored 1.000 (48/48) after one more rule surfaced: an answer opening with Because… is a subordinate clause with no main-clause proposition, and the judge scored it 0 — the three such answers were rewritten and --freeze-golden now rejects them. The review found a trap worth remembering: five drafted answers were one word (Three, 8GB, Postgres…). The scorer splits answers into claims of ≥10 characters and the judge never sees the question — so a bare 'Three' is not a checkable claim and would score 0.00 no matter how correct. Those answers were rewritten as full sentences, and --freeze-golden now rejects any answer that yields zero claims (evals.ValidateGolden, tested).

Try it yourself

head -3 evals/golden/v1.jsonl. Pick one, open the doc in corpus/, and check the answer yourself. Then try to freeze a file with the answer "Three" — it's rejected at that line.

Interview questions

Q Why not write the 30 pairs by hand?
A Drafting is the mechanical part — a model does it in minutes from the chunks. Reviewing is the judgment part — that stays human. It's how DeepEval/RAGAS synthesizers are meant to be used.
Q Why freeze with a hash?
A So every eval run records exactly which golden version it scored against. If the file changes, the hash changes, and old runs aren't compared to new ones.
Q What did the review actually catch?
A Nothing factually wrong — but five one-word answers that the claim splitter would have dropped, scoring 0.00 silently. The fix was full-sentence answers plus a freeze-time check for 'zero scorable claims', so the class of bug can't come back.

Remember

  • Model drafts, human reviews 100%.
  • Freeze = validate + sha256; reject zero-claim answers.
  • A golden answer must be a standalone sentence — the judge never sees the question.
