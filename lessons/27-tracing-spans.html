Part 6 · Traces and observability

Tracing: trace_id, span_id, parent_id

In one sentence

A trace is the story of one request; a span is one step in it. Every span carries trace_id (which story), span_id (which step) and parent_id (which step came before).

Why it exists

Metrics tell you 'p99 got worse'. Traces tell you 'request 598d… spent its time in model.generate'. This is the OpenTelemetry data shape, which is what Langfuse and Phoenix ingest — so a real tool could read these spans later.

How it works in this project

-- the table (0001_init.sql)
spans(trace_id, span_id, parent_id, name, started_at, attrs JSONB)   PRIMARY KEY (trace_id, span_id)

// router/server.go — a chat emits 3 spans, chained
route.decide     parent=""            attrs {"tier":"fast","reason":"short-simple-prompt"}
model.generate   parent=decideSpan    attrs {"model":"qwen2.5:3b-instruct"}
router.respond   parent=genSpan       attrs {"model":"..."}

// tracker/tracker.go — a workflow emits 1 span per step, trace_id = workflow_id
researcher / drafter / reviewer   attrs {"seq":0,"output_snippet":"first 200 chars"}

Reading them back: GET /v1/traces/{id}, go run . --trace <id>, or the MCP tool inspect_trace — all three call the same ListSpans, which runs RedactAttrs to drop prompt/input/text/output keys. Prompts never leave the database through the read path.

Unknown id → 404 {error:{code:"trace_not_found",…}} over HTTP, -32004 over MCP (used to be 200 {spans:null}; fixed in the live pass).

Try it yourself

curl -s localhost:8080/v1/chat/completions -d '{"prompt":"hi"}' | jq .trace_id
curl -s localhost:8080/v1/traces/<trace_id> | jq '.spans[] | {name, parent_id}'

Interview questions

Q What's the difference between a trace and a span?
A A trace is the whole request (one id). Spans are its steps; each has its own id and points to its parent. Together they form a tree you can render as a timeline.
Q Why redact on read?
A Prompts may contain user data. Storing them lets me debug; redacting on every read path (HTTP, CLI, MCP) means no consumer sees them by accident. Retention is 30 days by policy.
Q Any known imperfection?
A Tracker step spans use parent_id = workflow_id (the trace id) instead of the previous span id. Router spans chain properly. It's cosmetic until you export to Langfuse; the fix is a root span — parked in the backlog.

Remember

  • trace_id = which request; span_id = which step; parent_id = the tree.
  • Router: 3 chained spans. Tracker: 1 span per step.
  • Redact on every read path.
