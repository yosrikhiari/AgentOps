What a deep review found (and why each bug mattered)

In one sentence

After the code was 'done', every file was re-read against a checklist; 15 findings came out, 14 were fixed the same day with a binding test each — then three more surfaced while writing these lessons and running the first full golden suite.

Why it exists

'Tests green' is not 'correct'. A structured review pass with categories (correctness, performance, resource use, error handling, …) finds the bugs tests were never written for. The list below is the best interview material in the project.

How it works in this project

  • Prometheus le label unquoted — every scrape would have been rejected. Grafana would have shown nothing. Caught by reading the exposition spec.
  • Histogram double-cumulated (found in the lessons pass) — buckets were filled cumulatively and summed again on output; p99 would have been fiction. Test: TestHistogramBucketsAreCumulativeOnce.
  • New DB connection per span, synchronously — DB down = +6 s per chat. Replaced with a pool + async writer.
  • ServeMux rebuilt per request — wasteful allocation on every call. Built once.
  • Retry on 4xx — a bad API key was retried with backoff. Now Permanent() stops it; 429 honours Retry-After.
  • Resume used the wrong input — a resumed workflow answered the new CLI's question. Stored input now wins.
  • Run header + pair scores not atomic — a crash could leave a run with no scores. Now one transaction.
  • Judge swap looked like drift — added judge_changed to the report.
  • max_tokens accepted and ignored — now forwarded as num_predict.
  • 'NOT SUPPORTED' parsed as supported — substring trap; negatives checked first.
  • Unknown trace returned 200 — now 404 / -32004.
  • Malformed MCP line silently dropped — now JSON-RPC -32700.
  • Failed chats invisible — added router_errors_total + a panel.
  • Recall > 1 (found on the first full golden run) — a doc's two chunks both retrieved counted as two hits against one relevant doc. Recall now counts unique docs.
  • Nondeterministic local judge (same run) — no temperature set on Ollama judge calls; one verdict flipped between runs. Pinned to 0.

The rule that made this possible: every fix ships with a test that fails on the old code (bind-check). Otherwise you don't know the test guards anything.

Interview questions

Q Tell me about a bug you found.
A The Prometheus histogram. Label unquoted → scrape rejected; and buckets summed twice → p99 wrong. Both invisible to the existing tests because they only checked that a histogram line existed. I fixed both and wrote tests that assert the exact cumulative values.
Q How do you review your own code?
A A separate pass, after 'done', with a fixed category list, reading every file top to bottom. Then fix with a binding test each, then re-run the live paths. Green tests before the pass didn't mean much — 15 findings.
Q What's a binding test?
A One that fails when you revert the fix. I check by actually reverting in a scratch copy. A test that passes either way is decoration.

Remember

  • Green tests ≠ correct.
  • Review with a category checklist, after 'done'.
  • Every fix gets a test that fails on the old code.
