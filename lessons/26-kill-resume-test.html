Part 5 · The durable task tracker

The kill -9 test

In one sentence

The proof of durability is a test where step 2 fails, the workflow is re-run with the same id, and step 1 is not executed again.

Why it exists

'It resumes' is a claim. An automated test that counts how many times each step ran is proof — and it runs in milliseconds with the in-memory store, so it can't rot.

How it works in this project

// tracker/tracker_test.go
researcher  := okFunc(&nR, "ctx: durable workflows")
drafterFail := func(...) { nD++; return "", errors.New("killed mid-drafter") }   // simulates kill -9
_, err := RunToy(ctx, store, "wf-kill", " durable?", researcher, drafterFail, reviewer)
// err != nil; researcher=done, drafter NOT done

drafterOK := okFunc(&nD, "draft: durable workflows resume")
final, err := RunToy(ctx, store, "wf-kill", " durable?", researcher, drafterOK, reviewer)   // SAME id
// nR == 1  ← researcher ran once across both runs (no duplicate side effect)
// nD == 2  ← drafter: 1 killed attempt + 1 successful
// nV == 1, all steps done, workflow status done

And the live version, against real Postgres + Ollama: started workflow f7850f82f56fe6b9, taskkill /F the process while drafter=running, DB showed drafter running attempts=1, --resume-tracker f7850f82f56fe6b9 finished it 38 s later with researcher attempts=1, drafter attempts=2, reviewer attempts=1.

Try it yourself

go test ./tracker/ -run TestKillResume -v. Then break it: comment out the if st.Status == StatusDone { continue } line and watch nR become 2.

Interview questions

Q How do you prove crash recovery?
A A test where a step function fails once, then the same workflow id is re-run with a working function, asserting each step's call count. Plus one real kill against Postgres, recorded in the plan.
Q What does 'attempts' tell you?
A How many times a step was started. attempts=2 with status=done means it was killed once and then succeeded — visible in the DB, no logs needed.
Q What's not handled?
A Two processes resuming the same id at once would both run the pending step. A SELECT … FOR UPDATE SKIP LOCKED lease fixes it; it's parked because a solo demo never hits it.

Remember

  • Fail step 2, re-run same id, count calls.
  • Researcher runs once; drafter attempts = 2.
  • Automated test + one recorded live kill.
