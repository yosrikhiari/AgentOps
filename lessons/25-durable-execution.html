Part 5 · The durable task tracker

Durable execution: workflows that survive crashes

In one sentence

Each step of a multi-step task writes its status to Postgres before and after running, so a restarted process can see where it was and continue instead of starting over.

Why it exists

An AI agent that does Research → Draft → Review takes a minute and costs tokens. If the process dies after Research, you don't want to pay for Research again — and you definitely don't want it to run twice if it had side effects. This is what Temporal and DBOS do; here it's ~250 lines over two tables (ADR-0003).

How it works in this project

workflows(id, type, status, input)              -- one row per workflow
steps(workflow_id, seq, name, status, output, attempts)   -- pending → running → done

// tracker/tracker.go — the whole algorithm
storedInput := store.EnsureWorkflow(ctx, id, "research-draft-review", input)  // INSERT ... ON CONFLICT DO NOTHING
steps := store.ListSteps(ctx, id)                                             // ordered by seq
for i, st := range steps {
    if st.Status == StatusDone { current = st.Output; continue }              // ← RESUME: skip finished work
    store.SetRunning(ctx, id, st.Seq)                                         // attempts = attempts + 1
    out, err := fns[i](ctx, current)                                          // the actual work
    if err != nil { return "", err }                                          // row stays 'running'
    store.SetDone(ctx, id, st.Seq, out)                                       // output saved
    store.EmitSpan(...)                                                        // one span per step
    current = out
}
store.SetWorkflowStatus(ctx, id, StatusDone)

Three ideas do all the work: (1) idempotency keys — (workflow_id, seq) is the primary key and inserts use ON CONFLICT DO NOTHING; (2) status rows — the step's row is the source of truth, not process memory; (3) resume = re-run the same workflow id — done steps are skipped, the pending one re-runs.

Try it yourself

go run . --run-tracker                       # prints workflow id, runs 3 steps (~45 s)
go run . --resume-tracker <id>               # nothing to do: all steps done

Interview questions

Q What is durable execution?
A Persisting workflow progress step by step so a crash loses at most the current step, and a restart continues from the last completed one.
Q Why not use Temporal or DBOS?
A Studied both. Temporal is a whole cluster; DBOS has a Go SDK but for three steps the pattern is two tables and one loop. I kept go.mod at stdlib + pgx and can explain every line. DBOS is parked as an alternative.
Q What's stored as the input on resume?
A The original input from the workflows row, not whatever the resuming process was launched with. A deep-review caught that the resume used the new flag value — now EnsureWorkflow returns the stored input and it wins.

Remember

  • Status rows in Postgres = the truth.
  • Resume = same id, skip 'done' steps.
  • Idempotency via (workflow_id, seq) + ON CONFLICT.
