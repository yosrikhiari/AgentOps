# ADR-0010 — Client-held conversation and capability-gated workflows (cockpit)

**Status:** proposed (2026-09-21) · **Context:** the cockpit merges send (#/try) and sight (#/live) on one surface, which raises two questions the v1.0 architecture never had to answer: where does conversational state live, and what happens when a conversation starts work that alters things. The tracker (`tracker/tracker.go:277` `RunToy`) runs three hardcoded, side-effect-free steps with `running`/`done` states only (no `failed` state, no resume lease — both documented limits); the gateway is stateless by privacy rule (prompts never persisted, `TestPolicyPromptsNeverReachSpans`).

**Decision.**

1. **Conversation lives in the client.** The cockpit keeps `messages[]` and resends history each turn through the unchanged OpenAI-shaped `POST /v1/chat/completions`; the gateway learns no sessions, keeps no retention policy, and `PRIVACY.md` stays true. History is capped (last 10 messages, newest-first truncation with a visible "truncated" chip) so token growth is a UI fact, not a surprise.
2. **Explicit trigger before clever trigger.** The cockpit gains a "Run as workflow" action that starts the existing toy runner with the last user message as input (`console` `StartWorkflow`, `POST /v1/workflows` — no backend change). An LLM intent classifier may later *suggest* the button, but it never *presses* it: auto-execution on model output turns prompt injection into remote execution.
3. **Capabilities are code, never model output.** When generic workflows (Track D) arrive, each step declares one capability class — `read` (run free), `write` / `external` (pause at `awaiting_approval` until `POST /v1/workflows/{id}/approve` with an authenticated approver recorded on the span). Unknown capability = refused (fail-closed, same shape as the routing rule in ADR-0007). The model proposes *arguments*; the allowlist owns *powers*.
4. **Durability gaps close before mutation ships.** The `failed` terminal state, an attempts cap, and the resume lease (`SELECT … FOR UPDATE SKIP LOCKED`) — all parked as known limits — are prerequisites for the first mutating step, not follow-ups. A failed mutating step must never auto-retry blindly.
5. **Audit everything, disclose storage.** Every step and every approval is a span; workflow *inputs are stored* in Postgres (unlike chat prompts) — `PRIVACY.md` must say so in the same change. Per-workflow token/step caps plus a runner kill switch bound the blast radius.

**Alternatives rejected.** *Server-side sessions* — a second store with retention and eviction for what `messages[]` resend already solves. *Model-gated auto-execution* — injection-to-RCE with no human in the loop. *Approval for everything* — read-only steps (retrieve, draft, judge) pausing for clicks would make the toy unusable; friction belongs exactly at the mutation boundary.

**Consequences.** The cockpit delivers conversation + "run it" with zero backend changes (P0–P2 of the plan); mutating power waits on Track D plus the three durability prerequisites. The threat model moves from "prompts never leak" to "actions never happen unauthorised" — enforced by `awaiting_approval` default-deny plus a bind-checked policy test per capability class.
