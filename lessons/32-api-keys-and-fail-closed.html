Virtual API keys and the fail-closed rule

In one sentence

Callers get virtual keys with a per-minute limit and a lifetime token budget; and a request flagged sensitive never reaches a cloud backend — even when every local model is down.

Why it exists

A gateway without keys is an open proxy to your GPU. A gateway that quietly falls back to a cloud API when Ollama dies will, one day, send a customer's IBAN to a third party. Both rules are cheap to build and expensive to bolt on later.

How it works in this project

go run . --create-key alice --key-rpm 60 --key-budget 2000000   # prints ak_… once; SHA-256 stored
Authorization: Bearer ak_…

401 missing_api_key / invalid_api_key     403 api_key_disabled / budget_exceeded     429 rate_limited (+ Retry-After)

// router/router.go — the plan is built ONCE, and the rule lives there
func Plan(requested string, msgs []Message, sensitive bool, refs []ModelRef) (Route, error) {
    // explicit cloud model + sensitive → ErrSensitiveCloud (403)
    // auto: chosen tier, then the other local tier, then cloud — cloud only if !sensitive
}

Sensitive is set by header X-AgentOps-Sensitive: true, by "sensitive":true in the body, or by a small keyword list (password, iban, passport, confidentiel…). The flag is written into the route.decide span, so every trace shows whether the rule applied.

Keys: only the hash is stored; the rate limiter is a fixed one-minute window per key in memory; usage is charged asynchronously after the response so a budget can overshoot by one request. Both trade-offs are written down in the plan.

Try it yourself

KEY=$(go run . --create-key demo --key-rpm 2 | grep -o 'ak_[0-9a-f]*')
for i in 1 2 3; do curl -s -o /dev/null -w "%{http_code} " localhost:8080/v1/chat/completions -H "Authorization: Bearer $KEY" -d '{"prompt":"hi"}'; done
# 200 200 429

Interview questions

Q Where exactly is the fail-closed rule enforced?
A In Plan(), once, when the candidate list is built. Sensitive requests simply never have a non-local candidate, so no later code path can leak — and an explicit cloud model is refused up front with 403.
Q Why store only a hash of the key?
A A database dump then reveals nothing usable. The secret is printed once at creation; lose it and you mint a new one.
Q What did the live test show?
A 401 without a key, 200 with one, then 200/429/429/429 on a 2-rpm key with a Retry-After header, and tokens_used climbing in the table.

Remember

  • Keys: hash stored, RPM window, token budget, one error shape.
  • Sensitive → cloud removed from the plan; explicit cloud → 403.
  • Trade-offs (per-process limiter, async charge) are documented, not hidden.
