Part 2 · The router

Seeing the numbers: Grafana dashboard and k6 load test

In one sentence

A Grafana dashboard stored as JSON draws the router's metrics in five panels, and a k6 script measures the router's own overhead at 50 requests/second.

Why it exists

Metrics nobody looks at are noise. Grafana turns the /metrics text into graphs; k6 turns 'the router is fast' into a measured p99. Both live in the repo as code so anyone can reproduce them.

How it works in this project

dashboard/grafana/router.json defines five panels:

  • Requests/sec by model — rate(router_requests_total[1m])
  • p99 latency by model — histogram_quantile(0.99, rate(router_latency_seconds_bucket[5m]))
  • Tokens total by model — router_tokens_total
  • Eval faithfulness — the gauge set after each eval run
  • Error rate by model — rate(router_errors_total[1m])

The router only exposes numbers. Prometheus scrapes them, Grafana draws them. That app → scrape → draw separation is the whole architecture of observability tooling.

load-tests/router.js is the load test:

scenarios: {
  overhead: { executor: 'constant-arrival-rate', rate: 50, timeUnit: '1s',
              duration: '1m', preAllocatedVUs: 10, exec: 'health' },   // /health: no model call
  chat:     { executor: 'per-vu-iterations', vus: 1, iterations: 2, exec: 'chat' },
},
thresholds: {
  'http_req_failed{scenario:overhead}':   ['rate<0.01'],   // <1% errors
  'http_req_duration{scenario:overhead}': ['p(99)<100'],   // p99 under 100 ms = pass/fail gate
  'checks{scenario:chat}':                ['rate>0.99'],
},

Hitting /health (no model) isolates the Go server's overhead from the model's think time. Honest note: the plan targets p99 overhead <5 ms; the script's gate is 100 ms. The gate is what makes the run pass or fail; the 5 ms is what you read off the report.

Try it yourself

docker compose --profile monitoring up -d       # Prometheus :9090 + Grafana :3000, dashboard already provisioned
go run .                                        # in one terminal
k6 run load-tests/router.js                     # in another; then open localhost:3000/d/agentops-router

Real run (2026-09-15): 0 failures out of 2,725 requests at 50 RPS, p99 = 70 ms (gate 100), median 1.47 ms, both chats 200. The p99 was measured while a 4.7 GB model download and a 3B chat shared the box — the median is the router's real overhead. Grafana came up with all five panels populated, faithfulness stat reading 0.969.

Provisioning detail that cost 20 minutes: Grafana's file provisioner needs each target to carry a refId and a fixed datasource uid; ${DS_PROMETHEUS} placeholders only work for manual import. The dashboard JSON now has both, so docker compose --profile monitoring up is the whole setup.

Interview questions

Q What does rate() do?
A Turns a counter that only goes up into 'how many per second over the last window'. Counters are useless raw; rate() makes them a graph.
Q Why hit /health and not the chat endpoint for overhead?
A Chat latency is 99% model time. /health measures only the Go server: parsing, routing, JSON. That's the router's overhead — 1.47 ms median, 70 ms p99 on a busy laptop.
Q How is the dashboard reproducible?
A The compose file has a monitoring profile: Prometheus with a scrape config for the host, Grafana with the datasource and dashboard provisioned from files in the repo. No clicking; it comes up populated.

Remember

  • Dashboard + datasource provisioned from the repo; 5 panels.
  • App exposes → Prometheus scrapes → Grafana draws.
  • k6: 0/2725 failed, p99 70 ms, median 1.47 ms.
