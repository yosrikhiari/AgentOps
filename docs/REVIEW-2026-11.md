# Tower — full codebase review (November 2026)

A review of the repository as it stands after the November 2026 audit pass, against the
problems it claims to solve, against comparable open-source systems, and against the
research literature. Rating is out of 10, broken down by dimension, with the reasoning
shown so the number can be argued with rather than asserted.

Baseline: `main` at `7a3c351`, `go test ./...` green, `go vet` clean, policy 19/19,
`govulncheck` clean, distroless image builds.

---

## 1. What Tower is, in one paragraph

Tower is a single Go binary that puts local and cloud LLMs behind an OpenAI- (and
Anthropic-) shaped HTTP gateway, keeps a multi-step agent alive across `kill -9`, scores
answers claim-by-claim against retrieved sources with drift alerting, emits one redacted
trace per request, exposes an MCP server, and ships an embedded web console. It is built
for one box (an 8 GB GPU) and is deliberately a modular monolith: stdlib + one dependency
(`pgx`), Postgres for durability, Ollama for models. The author is explicit that it is
proof-of-competence software first and a product second, and the docs say so.

## 2. Architecture — 9/10

**Strengths.** The modular monolith is the right call for the constraint set and the README
argues it honestly (ADR-0003: durability by row state, not events; broker deferred until a
second worker exists). Packages talk to the database through tiny interfaces
(`Execer/Queryer/Rows`) and only `main.go` imports pgx (ADR-0001), which makes the whole
gateway testable offline in ~2 s. The sync/async split is disciplined: the request path
does exactly authenticate → parse → plan → call → respond, and every edge (spans, usage
charge, evals, workflows, health probes) is bounded, non-blocking, observable and
idempotent (RULES §5). The span sink is a `select … default` with a 1024-deep channel and
a single writer, verified by policy test. Fail-closed routing is real: sensitive requests
have every non-local candidate removed including the primary, and Ollama `:cloud` models
are treated as non-local.

**Weaknesses.** The "one process serves one GPU" ceiling is stated, not tested for a second
replica; the API-key limiter and eval single-flight are per-process, and two resumers of one
workflow id both run the pending step. Those are documented limits, not hidden bugs, but
they cap the score at 9 rather than 10. The request-timeout path now benches the backend
(after the November fix), which closes the main latency-tail hole.

## 3. Code quality — 8.5/10

**Strengths.** `gofmt`, `go vet`, `staticcheck`, `govulncheck`, `-race` all clean. One direct
dependency, Dependabot grouped, CI pinned to commit SHAs. 19 executable policy tests that
fail the build when a rule breaks — this is the single most unusual and valuable thing in
the repo. Error handling is consistent: one JSON error shape (`{error:{code,message,trace_id}}`)
everywhere, including 404/405 that previously fell through to net/http's plain text. Inputs
are validated (body cap 4 MiB, resource option ceilings, model presence). Redaction is
defence in depth: `RedactAttrs` at write time and again in the OTLP exporter.

**Weaknesses.** `main.go` is 80 KB and is the one file that does too much (flag parsing,
migrations, probing, mux wiring, OTLP, shutdown). It is the natural place for a
`cmd/` or `internal/bootstrap` split, and the low `main` package coverage (14.6%) is a
symptom: most CLI modes are exercised only by live runs, not tests. `sortStrings` was
hand-rolled insertion sort until this pass. `chargeKey` still spawns a goroutine per
request (audit §5.3, open). Coverage on `console` (66.1%) and `tracker` (68.5%) leaves
the Postgres-down path and resume edge cases less exercised than the happy path.

## 4. Testing — 8/10

**Strengths.** The pyramid is right: unit tests with fakes at the I/O boundary, wire-format
tests replaying real bytes (Ollama NDJSON, OpenAI SSE, Prometheus exposition), policy
tests, and recorded live verification with numbers. The bind-check discipline (every fix
ships with a test that fails on the old code, verified by reverting in a scratch copy) is
the thing that makes the correctness claim credible. Fuzzing now covers `parseVerdict`.
The judge audit (`--judge-audit`) is a genuinely good idea: it measures the detector
itself against a labelled set, with precision/recall, false-alarm rate, decision flips and
Cohen's κ, instead of trusting agreement.

**Weaknesses.** No property tests for the fail-closed routing rule (hand-written cases only).
No fuzz on the request decoders or SSE emitters. The k6 gate is `/health` only; a mixed
workload gate (short fast + long quality + streaming) would measure router overhead where
it actually matters. The gold set is 35 items, not the 50 recommended, and the second
judge (phi4-mini) fails the audit, so κ = 0.64 is moderate rather than strong.

## 5. Security — 8/10

**Strengths.** STRIDE-lite table in RULES §9 with a control and an enforcement test per
threat. Prompts never reach spans (policy test with a canary). Sensitive requests never
reach a cloud backend (policy test). Container runs as nonroot on distroless. Console is
loopback-only by default with `consoleGuard`; key creation is CLI-only on the box. Body
cap, option ceilings, rate limits, budgets all enforced. `govulncheck` runs in CI and
already found and fixed GO-2026-5970. Agent-config files are scanned for secret shapes,
pipe-to-shell, chmod 777, disabled host-key checks.

**Weaknesses.** `/metrics` is unauthenticated (documented gap). `CONSOLE_REMOTE=true` is
all-or-nothing. MCP tool proxying is not implemented yet, and the description-pinning
control (research §2.6) must land before it does. The threat model beyond the table is
backlog (A7). These are stated gaps, not surprises, which keeps the score at 8 rather than
lower.

## 6. Performance — 8/10

**Strengths.** Router overhead budget is defined and measured (p50 < 5 ms, p99 < 100 ms at
50 RPS; recorded 1.47 ms / 70 ms, 0/2725 failures). Backends that are down are skipped,
not tried. Exhaustion tracking benches quota/transient failures. Span writes are
non-blocking. The parallel probe (this pass) removes a serial wait. Retention windows are
clamped so a bad env var cannot empty a table.

**Weaknesses.** No shared HTTP transport (each backend builds its own), no circuit breaker
for up-but-slow backends beyond the transient bench, no request-level caching/dedup. The
streaming path holds a goroutine for the whole generation with no concurrency cap. These
are all in the audit as P2/P3 and are cheap; the absence of numbers for them (no mixed
workload gate) is the bigger gap.

## 7. Observability and traces — 9/10

**Strengths.** One trace per request with `trace_id/span_id/parent_id`, prompts never stored,
three spans per chat (`route.decide → model.generate → router.respond`), redacted read paths
everywhere, OTLP export with dual-named `gen_ai.*` attributes beside the internal names
(because the GenAI semconv is still `Development`), prompts never exported, batched and
strictly lossy. The trace inspector, MCP `inspect_trace`, CLI `--trace`, and console all
read the same store. GPU samples correlated to spans. This is the strongest part of the
product and the part most likely to be genuinely useful to someone else.

**Weaknesses.** Only the OTLP/HTTP JSON encoding is implemented (no gRPC), and the exporter
has no status surface beyond the new `/v1/otlp/status`. Semconv version is pinned but
re-checking it on every release is manual.

## 8. Developer experience and documentation — 9/10

**Strengths.** README is excellent and honest (MVP checkboxes, known limits, every flag).
`docs/API.md` documents every env var and endpoint (enforced by policy). `docs/RULES.md`
is a real rule book with enforcement columns. 33 lessons with interview Q&A, ADRs indexed.
The Tower design system page is the console contract. `--help` covers every mode. The
commit-message convention is written down. This is the rare solo project where the docs
are better than most team projects.

**Weaknesses.** `main.go`'s size (above). The `docs/plans/` directory is gitignored, so the
track history lives only locally; a reader of the repo cannot reconstruct how the work
was sequenced from git alone (CHANGELOG covers the what, not the how).

## 9. Comparison with similar solutions

| System | What it does best | Where Tower stands |
|---|---|---|
| **LiteLLM** (Python, 100+ providers) | Provider coverage, the de facto standard | Tower cannot and does not try to win this race; it wins on explainability and single-binary operability |
| **Bifrost** (Go, 20+ providers, ~0.7 ms p99) | Raw throughput and provider breadth in Go | Tower's router overhead is comparable (1.47 ms p50) but it does far less provider work; Bifrost is the honest benchmark to beat if Tower ever chases throughput |
| **TensorZero** (Rust gateway + ClickHouse) | Production-grade observability at scale, feedback-driven optimization | Tower is a single box with Postgres; TensorZero is the "what you grow into" answer. Tower's value is being readable end to end |
| **Langfuse** (TS/Python, hosted or self-host) | Trace UI, eval datasets, prompt management | Tower's trace shape is Langfuse-compatible (OTLP), and its console is lighter but narrower. Langfuse is the reference for "what a trace UI should look like" |
| **Temporal** | Durable execution, exactly-once, signals, queries | Tower's row-state durability is a deliberate subset: no signals, no queries, no exactly-once beyond idempotency keys. Right for the scope, and the ADR says so |
| **AgentOps.ai** (funded, agent observability) | Brand, agent-specific evals, hosted | Name collision is real and the research doc says so; this is a positioning decision, not code |

**Honest read.** Tower is not competing with any of these on features. Its position is the
intersection of "runs on one box", "no SaaS account", "every line explainable", and "has
evals and traces at all". That intersection is genuinely underserved, and the docs are
honest about where the line is. The weakest comparison point is provider coverage, which
the project correctly refuses to chase.

## 10. Alignment with the research literature

The November research sweep (`RESEARCH-2026-11-next-steps.md`) identified seven work items.
Status after this review:

1. Judge validity pack — **code done, measured.** qwen3:8b passes; phi4-mini fails; κ 0.64.
2. Real v3 baseline + ceiling metrics — **partially done** (`--score-model`, `--route-replay`,
   `--ceiling` exist; a full 72-pair judged run still needs a quiet GPU).
3. 3-way claim labels — **done.**
4. OTLP export, dual-named and pinned — **done.**
5. Trajectory eval for workflows — **not done** (spans exist, no grading beyond one-shot
   `--workflow-grade`).
6. Routing Phase 1 — **done** (`ROUTER_POLICY`).
7. Name decision — **open.**

The literature-backed corrections the project made are the right ones: the
*Unsolvability Ceiling* and *Co-Failure Ceiling* results are reflected in the `unsolvable`
and ceiling metrics; the *Reliability without Validity* position-bias finding is reflected
in the judge audit and the trustworthy-verdict rate; the cache-aware routing literature
(CacheRoute, GORGO) corrected an over-strong "no paper models this cost" claim. The one
piece the literature says to do and the project has not is outcome-state grading for
workflows (τ-bench), which is also the largest uncovered product surface.

**Overall: 8.5 / 10.**

The score is high because the project does what it says, measures it, and says honestly
where it stops. It is not a 10 because the measured gaps are real and unaddressed:
moderate judge agreement, no workflow trajectory grading, no mixed-workload perf gate,
per-process limits, and an 80 KB `main.go`. None of those are hidden; several are
explicitly on the roadmap. A 9 would require closing the workflow-grading surface and
getting κ above 0.8 with a stronger second judge; a 10 would additionally need the
replica story (shared limiter, `SKIP LOCKED` leases) that the project correctly defers.

## 12. What would move the needle fastest

1. Run the v3 baseline on a quiet GPU and publish the number (§1.2 of the audit).
2. Add trajectory grading for workflows (τ-bench style) — the biggest uncovered surface.
3. Cross-check the judge with Groq llama-3.3-70b and get κ above 0.8.
4. Split `main.go` into `internal/bootstrap` and add a mixed-workload k6 gate.
5. Decide the name before any public launch.
