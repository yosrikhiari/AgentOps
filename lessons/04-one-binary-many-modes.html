One binary, many modes

In one sentence

The same executable is a web server, an MCP server, a migration tool, an eval runner and a workflow runner — chosen by a command-line flag.

Why it exists

A solo project should not ship six binaries. One binary means one build, one Docker image, and every mode shares the same config and code paths — so the stats the MCP server reports are the same stats the HTTP server counts.

How it works in this project

In main.go, main() parses flags, and each 'and exit' mode returns early:

mcpMode      := flag.Bool("mcp", false, "run as MCP stdio server instead of HTTP router")
migrate      := flag.Bool("migrate", false, "apply SQL migrations and exit")
ingest       := flag.Bool("ingest", false, "embed clean corpus into pgvector and exit")
search       := flag.String("search", "", "cosine-search the corpus for QUERY and exit")
draftGolden  := flag.Bool("draft-golden", false, "draft golden QA pairs with local LLM and exit")
freezeGolden := flag.Bool("freeze-golden", false, "validate evals/golden/v1.jsonl and freeze hash")
score        := flag.Bool("score", false, "run faithfulness + retrieval suite and exit")
driftFlag    := flag.Bool("drift", false, "print drift report and exit")
scheduleEvals:= flag.String("schedule-evals", "", "run eval suite every INTERVAL forever")
runTracker   := flag.Bool("run-tracker", false, "run toy workflow and exit")
resumeTracker:= flag.String("resume-tracker", "", "resume toy workflow ID and exit")
traceID      := flag.String("trace", "", "print redacted spans for TRACE_ID and exit")
createKey    := flag.String("create-key", "", "mint an API key NAME, print the secret once, exit")   // v1.0
showVersion  := flag.Bool("version", false, "print version and exit")                               // v1.0
flag.Parse()
if *migrate { runMigrate(dsn); return }
if *ingest  { runIngest(dsn, cfg.OllamaURL); return }
// ... one if per mode ...
// no flag → pgx pool, backends + health prober, API-key store, router, console, MCP wiring, HTTP server with graceful shutdown

The CLI modes open one short-lived connection (connect, do the work, exit). The long-running server mode opens a connection pool because it handles many requests.

Try it yourself

Run go run . --help. Every mode is listed with a one-line description. Nothing is hidden.

Interview questions

Q Why flags instead of subcommands (like agentops migrate)?
A Flags were the simplest thing that works with the standard library flag package. Subcommands would be nicer at scale; for 12 modes flags are fine and need zero dependencies.
Q Isn't a scheduler a separate service normally?
A Yes, but ADR-0006 says: a scheduler here is --schedule-evals 24h, a loop in the same binary. Any cron or systemd timer can run it. Zero new deps.
Q How does the MCP mode share stats with HTTP mode?
A Both call the same router.Server.Chat() method, so the same in-memory counters get incremented no matter who asks.

Remember

  • Flags pick the mode; each mode returns early.
  • CLI modes: one connection. Server mode: a pool.
  • Shared code paths keep stats honest.
