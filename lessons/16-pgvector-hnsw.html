pgvector and HNSW: vector search inside Postgres

In one sentence

Instead of a separate vector database, the chunks and their 768-number embeddings live in Postgres with the pgvector extension and an HNSW index.

Why it exists

One database to run, back up and reason about. The tracker and evals already need Postgres; adding Qdrant or OpenSearch would be a second container for a 16-chunk corpus. pgvector is the decision (ADR-0004).

How it works in this project

-- migrations/0001_init.sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE chunks (
  id SERIAL PRIMARY KEY,
  doc_id TEXT NOT NULL REFERENCES docs(id),
  hash TEXT NOT NULL UNIQUE,
  text TEXT NOT NULL,
  embedding vector(768),           -- nomic-embed-text produces 768 dims
  ...
);
CREATE INDEX chunks_embedding_hnsw ON chunks
  USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 128);

-- evals/corpus.go — the search
SELECT doc_id, hash, text, source FROM chunks
ORDER BY embedding <=> $1::vector LIMIT $2;     -- <=> is cosine distance

HNSW (Hierarchical Navigable Small World) is a graph index for approximate nearest-neighbour search. m=16 = links per node, ef_construction=128 = how hard it works while building. Defaults are fine at this size; they matter at millions of rows.

The compose file uses the pgvector/pgvector:pg16 image, so the extension is already installed.

Try it yourself

docker compose up -d
go run . --migrate
docker exec -it agentops-postgres psql -U agentops -c "SELECT count(*) FROM chunks;"

Interview questions

Q Why pgvector over Qdrant/OpenSearch?
A Zero extra containers, one backup, and I already run Postgres for workflows. At solo scale the vector DB's extra features don't pay for the extra ops. I've used all three; the hybrid BM25+vector tuning is parked in the backlog.
Q What does <=> mean?
A pgvector's cosine-distance operator. Smaller = more similar. ORDER BY it, LIMIT k, and you have top-k retrieval.
Q What's the difference between exact and HNSW search?
A Exact compares the query to every row (fine for 16 rows). HNSW walks a graph and is approximate but stays fast at millions. The index is there so the code path is production-shaped.

Remember

  • Vectors in Postgres via pgvector.
  • <=> is cosine distance; ORDER BY it, LIMIT k.
  • HNSW m=16, ef_construction=128.
