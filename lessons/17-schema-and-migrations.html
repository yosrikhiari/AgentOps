The database schema and migrations

In one sentence

Seven tables in two SQL files, applied in filename order by a 20-line Go function.

Why it exists

Schema in versioned SQL files is the simplest migration system that works. Every table maps to one tool, so the schema is also a map of the project.

How it works in this project

docs / chunks               ← RAG corpus (evals)
workflows / steps           ← durable tracker
spans                       ← traces (router AND tracker write here)
eval_runs / eval_pair_scores← eval history for drift (0002_drift.sql)

-- evals/corpus.go
func Migrate(ctx, db Execer, dir string) error {
    files, _ := filepath.Glob(filepath.Join(dir, "*.sql"))
    sort.Strings(files)                       // 0001_ before 0002_
    for _, f := range files { db.Exec(ctx, readFile(f)) }
}

Every statement is CREATE ... IF NOT EXISTS, so re-running --migrate is safe. There is no migrations table tracking what was applied — fine while every migration is additive; the moment one needs ALTER, add a schema_migrations table.

Key indexes: (workflow_id, seq) primary key on steps, spans(trace_id), eval_runs(golden_version, created_at DESC) for 'last two runs' queries.

Try it yourself

cat migrations/0001_init.sql and find the one ON DELETE CASCADE in 0002_drift.sql: deleting an eval run removes its per-question scores.

Interview questions

Q Why two migration files?
A 0001 was the MVP schema. 0002 added eval_pair_scores when drift reporting needed per-question scores (ADR-0005). You never edit an applied migration; you add a new one.
Q What's the weakness of this migration approach?
A No applied-versions table, so it relies on IF NOT EXISTS. Works for additive changes only. I'd add schema_migrations before the first ALTER.
Q Why is spans keyed on (trace_id, span_id)?
A A span is unique within its trace. The composite key plus ON CONFLICT DO NOTHING makes span writes idempotent — retrying a write can't duplicate.

Remember

  • 7 tables, 2 SQL files, sorted by name.
  • IF NOT EXISTS makes re-runs safe.
  • Never edit an applied migration; add a new one.
