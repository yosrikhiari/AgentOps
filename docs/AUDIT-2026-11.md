# Tower — full codebase audit (November 2026)

Companion to `docs/RESEARCH-2026-11-next-steps.md` (what the evidence says to build) and
`docs/tower-enhancements.html` (the console backlog with live demos). This document is the
**engineering** audit: what the code does today, where it is soft, and what to change, in
priority order. Every item cites the file or policy it touches and, where useful, the
research that supports it. Nothing here contradicts `docs/RULES.md`; where an item would
need a new rule, it says so.

Baseline at audit time: `go test -race ./...` green on all packages, `go vet` clean,
`policy/policy_test.go` 19/19 green, `main` on commit `96ded77`.

---

## 0. Already shipped (do not re-propose)

These are done and should be treated as load-bearing, not as open work:

- 3-way claim labels (entailed / contradicted / baseless) + `parseVerdict` fail-closed (`evals/judge.go`)
- OTLP export, dual-named, pinned `ScopeVersion`, prompts never exported (`tracker/otlp.go`, `main.go` otlpExporter)

## 1. P0 — make the number defensible (1–3 days each)

### 1.1 Judge validity pack (research §2.4, §4 #1)

**What.** A 50-pair human-labelled gold set in `evals/golden/judge-audit.jsonl` (schema already
exists) plus a second judge (`phi4-mini` locally, or any 7B/8B when the card allows, or Groq
via `--judge2-backend groq`). Report precision/recall of "refuted", Cohen's κ, and a
trustworthy-verdict rate (per *All Verdicts are Not Equal*), not just agreement. The
context-order flip probe (`--judge-audit`) already detects label-vs-decision flips; add an
AB/BA replicate to separate position bias from genuine disagreement.

**Why.** Qwen3-8B (our production judge) has the highest measured position bias (0.192) in
*Reliability without Validity* (21 judges, ~541k judgments). A faithful paraphrase already
scored 0.00. Every drift alert and release gate inherits this.

**Kill criterion.** κ < 0.4 → stop tuning the judge and label more data.

**Files.** `evals/audit.go`, `evals/judge.go`, `main.go` (`--judge-audit` path), new
`docs/JUDGE-VALIDITY.md`.

### 1.2 A real v3 baseline + ceiling metrics (research §4 #2)

**What.** Ingest the corpus (`python scripts/clean_docs.py && go run . --ingest`) and run
`--score` on all 72 pairs, then report `unsolvable` (retrieval miss or all claims refuted) and
`smallest-tier-optimal` share in `--route-replay`. Add `co_failure_rate` (β) computation once
two models have outcomes on the same questions; report "undefined — one model" honestly today.

**Why.** The project currently has *no valid v3 measurement* (72/72 unjudged). The
*Unsolvability Ceiling* paper shows standard routers collapse to majority-class prediction
when verbosity/truncation artifacts are controlled; we must report the same controls or
publish inflated headroom.

**Files.** `evals/ceiling.go`, `router/decision.go` (add `router_policy` label to the record),
`docs/EVALS.md`.

### 1.3 Judge prompt hardening

**What.** The current prompt asks for 1–2 sentences of justification *before* the verdict. That
is chain-of-thought, which helps weak judges but costs tokens. Add a second prompt variant
(`faithfulness-v3`) that asks for the verdict first, then evidence, and run `--judge-audit`
against both on the gold set. Keep the better one; bump `JudgePromptVersion`.

**Why.** *Reliability without Validity* attributes most validity loss to prompt shape, not
model size. A 1-hour experiment, zero infra.

**Files.** `evals/judge.go` (`JudgePromptVersion`, `faithfulnessPrompt`).

## 2. P1 — product surface that is genuinely uncovered (3–5 days each)

### 2.1 Trajectory eval for workflows (research §2.5, §4 #5)

**What.** Per-step pass/fail, tool-call count, token cost, and pass^k over repeats, stored in
`eval_runs`-style rows (`workflow_runs`, `workflow_step_scores`). Grade with an LLM rubric
(`--workflow-grade` already exists for one workflow) and show a chip on `#/workflows`. Compare
the final state, not the transcript (τ-bench pattern), once the toy workflow gains side
effects.

**Why.** The workflow runner has spans but no grading; this is the largest uncovered surface
and what agent-observability buyers now ask for. Also the cheapest differentiator vs.
Langfuse/AgentOps.ai.

**Files.** `tracker/trajectory.go`, `evals/workflow_grade.go` (new), `console/store.go`,
`console/static/app.js`.

### 2.2 Export-routing-data + Phase 2 offline classifier (ML-ROUTING §4–7)

**What.** Add `--export-routing-data` (JSONL of `route_decisions` joined with spans and eval
scores). Add `ml/train_router.py` (scikit-learn logistic regression) and `router/learned.go`
(pure-Go scorer, sub-millisecond, weights from `models/router-weights.json` pointed at by
`ROUTER_WEIGHTS`). Log the weights hash in span attrs and show it on `#/models`. Fall back to
the heuristic when weights are absent (already the default path).

**Why.** Phase 1 (LLM-as-classifier) adds ~100 ms to every request and depends on Ollama on
the request path. Phase 2 removes both. Only honest after §1.2's ceiling metrics exist.

**Kill criterion.** If the learned model does not beat the heuristic on the held-out golden set,
ship nothing and keep the heuristic.

**Files.** new `ml/`, `router/learned.go`, `main.go` flag, `router/metrics.go` counters.

### 2.3 Anthropic Messages: tool passthrough

**What.** `router/anthropic.go` currently rejects `tools` with a 400. Add translation to/from
the OpenAI tool shape so Claude-Code-style clients can use Tower as an Anthropic-shaped
gateway to local models that support tools (qwen2.5 has tool calling).

**Why.** The README already advertises the Anthropic shape; rejecting tools is the one gap
that makes the claim "text only" honest but limits usefulness. Also unblocks a whole client
ecosystem.

**Files.** `router/anthropic.go`, `router/params.go` (tool schema), new tests in
`anthropic_test.go`.

### 2.4 OTLP transport polish

**What.** The exporter exists and is lossy by design. Add (a) a `--otlp-endpoint` flag as an
alternative to the env var, (b) a `/v1/otlp/status` endpoint reporting queue depth and dropped
count, (c) retry with exponential backoff on 5xx from the collector (currently one attempt).
Keep the "never block the request" rule (`select … default`).

**Why.** Operators cannot tell whether export is working today. The dropped counter is the only
signal, and it is not exposed.

**Files.** `main.go` otlpExporter, `console/handler.go`, policy test for non-blocking.

## 3. P2 — resilience and operability (1–2 days each)

### 3.1 Backend circuit breaker / cooldown

**What.** Today a backend that is up-but-slow (TCP accepts, then hangs until `REQUEST_TIMEOUT`)
is tried on every request because `Up()` is true. Add a per-backend cooldown: after N
consecutive failures or one timeout, mark it "cooling" for `COOLDOWN` (default 30 s) and skip
it in planning, logging the transition. Reset on the next successful probe.

**Why.** Health probes catch "down", not "degraded". A flapping Ollama turns every request
into a 300 s wait. This is the single biggest latency-tail risk.

**Files.** `router/backend.go` (HealthProber), `router/router.go` (plan filtering), new policy
test `TestPolicyCoolingBackendSkipped`.

### 3.2 Shared HTTP transport

**What.** Each backend constructs its own `http.Client` with a fresh transport. Build one
`tunedTransport` (MaxIdleConns, IdleConnTimeout, TLS handshake timeout) in `main.go` and
inject it. Add `OTLP`/Ollama keep-alive reuse.

**Why.** Connection churn under k6 (the 50 RPS gate) is measurable; a shared transport is the
standard fix and removes ~ms of per-request DNS/TLS work for cloud backends.

**Files.** `router/ollama.go`, `router/openai_backend.go`, `main.go`.

### 3.3 Bounded, observable request queue for streaming

**What.** Streaming holds a goroutine for the whole generation. Add a `MAX_CONCURRENT_STREAMS`
limit (default 0 = unlimited, matching today) with a 503 `streams_exhausted` + Retry-After
when exceeded, and a metric. Off by default to preserve today's behaviour.

**Why.** A single slow model call can exhaust goroutines on a small box. Opt-in, so no
behaviour change unless configured.

**Files.** `router/server.go`, `router/metrics.go`.

### 3.4 Retention + compaction for `spans`

**What.** `SPAN_KEEP` already prunes by age. Add an optional `SPAN_COMPACT_AFTER` (default
off) that collapses `model.generate` spans older than N days to `{model, latency_s, tokens,
error}` (drop attributes). Keeps the debugging surface for recent traffic, saves disk.

**Why.** A long-running gateway's `spans` table is the largest; compaction is the standard
answer and is reversible (no data needed for old traces).

**Files.** `main.go` (sweep), `tracker/spans.go`.

## 4. P3 — security hardening (each is a documented gap today)

### 4.1 Authenticate `/metrics`

**What.** Today `/metrics` is unauthenticated (documented in RULES §9). Add `METRICS_TOKEN`
env var; when set, require `Authorization: Bearer <token>` or a loopback peer. Default unset =
today's behaviour (so no breakage), but the README's quickstart should set it.

**Why.** Routing metadata and per-key counters leak to anyone who can reach the port. Low cost,
high value for anyone publishing the port behind a proxy.

**Files.** `router/metrics.go`, `main.go`, `docs/API.md`.

### 4.2 MCP tool description pinning (research §2.6)

**What.** We are an MCP *server* today, so exposure is limited. Before adding any MCP *client*
/proxy capability (a real feature request, since it would let Tower aggregate tools), implement
description pinning by hash and a provenance record, and treat tool results as untrusted
input in the fail-closed policy. Add a policy test: a tool result containing a prompt-shaped
string never reaches a span or a model prompt verbatim.

**Why.** Tool poisoning and rug pulls (CVE-2025-54136, OWASP ASI01/ASI02) arrive through
descriptions, not user text. The moment we proxy, this becomes the binding control.

**Files.** `mcp/server.go`, `policy/policy_test.go` (new test), `docs/RULES.md` §9.

### 4.3 Console remote mode: per-route auth

**What.** `CONSOLE_REMOTE=true` opts out of the loopback guard entirely. Add a lighter mode:
`CONSOLE_TOKEN` requires a bearer token on every console route while keeping the guard. Document
the three modes (loopback default / token / full remote behind a proxy).

**Why.** Operators want remote dashboards without giving up all auth. Today it is all-or-nothing.

**Files.** `console/handler.go` (consoleGuard), `main.go`, `docs/API.md`.

## 5. Code-level optimizations (small, each < 1 day)

1. **`sortStrings` in `tracker/otlp.go`** is insertion sort (O(n²)) over attribute names;
   replace with `sort.Strings`. Microscopic but free.
2. **`WithRetry` jitter** uses `rand.Int63n` on a global source; fine, but make it injectable
   for tests (deterministic backoff assertions).
3. **`chargeKey`** spawns a goroutine per request; under 50 RPS that is 50 goroutines/s.
   Replace with a single worker draining a 1024-deep channel (drop + count on full), matching
   the span-sink pattern. Policy test already codifies that pattern.
4. **`HealthProber.ProbeOnce`** serializes backends; parallelize with a WaitGroup (each probe
   has its own 5 s timeout). Probe time = max, not sum.
5. **Console store queries** build `[]any` args by hand; a small query builder or generated
   code reduces the boilerplate and the chance of arg-order bugs. Review-only; not a policy.
6. **`params.go` option ceilings** are hardcoded; move to a struct with `validate()` so new
   options get checked by construction.
7. **Static analysis**: run `staticcheck` and `govulncheck` are already in CI; add
   `golangci-lint` (errcheck, gosimple, unused) as an advisory job. Not a gate, to avoid
   noise, but it catches dead code.
8. **Fuzz the parsers**: `parseVerdict`, the OpenAI/Anthropic request decoders, and the
   SSE emitters are pure functions with clear contracts. `go test -fuzz` on them costs little
   and catches malformed-input panics.

## 6. Testing & measurement gaps

1. **No fuzzing** anywhere (see 5.8). Add `FuzzParseVerdict`, `FuzzDecodeChatRequest`.
2. **No property tests** for the router's fail-closed rule: generate random sensitive/non-sensitive
   request sets and assert no non-local candidate ever appears. The existing tests are
   hand-written cases; a property test is strictly stronger.
3. **Console**: the `console_test.go` suite is 24 k lines but largely happy-path. Add a test for
   the Postgres-down path on every endpoint (the enhancements doc's sprint 1 explicitly
   wants it).
4. **Load**: k6 gate is `/health` only. Add a mixed-workload gate (short fast + long quality +
   streaming) with a p99 budget, so router overhead is measured where it actually matters.
5. **Judge audit gold set** is empty today; §1.1 covers filling it. Until then, every eval
   number is ungrounded.

## 8. Explicit non-goals (do not propose)

Carried over from `docs/RULES.md` §1 and the research doc §5. Proposing these is a waste of
review time:

- A hosted/multi-tenant product.
- A vector-database bake-off or replacing pgvector.
- Provider coverage as a goal (LiteLLM has 100+, we cannot win that race).
- Deep learning in Go or an ML platform (MLflow, feature store, Kubernetes).
- Online learning from user feedback (no signal exists; would be gaming itself).
- Semantic-entropy detection on a 4 GB card.
- MCP tool proxying without description pinning (§4.2 must land first).
- A learned router before β and the ceiling metrics exist (§1.2 must land first).

## 10. Measured results (2026-11-22)

Live run: `tower --judge-audit --judge2-model phi4-mini:3.8b` over the 35-item
`evals/golden/judge-audit.jsonl` set, both judges at temperature 0, flip probe enabled.

| Judge | TP | FP | FN | TN | Precision | Recall | False alarm | Decision flips | Stable | Verdict |
|---|---|---|---|---|---|---|---|---|---|---|
| qwen3:8b | 18 | 1 | 0 | 16 | 0.95 | 1.00 | 0.06 | 0/16 | 1.00 | PASS |
| phi4-mini:3.8b | 18 | 7 | 0 | 10 | 0.72 | 1.00 | 0.41 | 2/16 | 0.94 | FAIL |

Agreement: n=35, Cohen's κ = 0.64.

Readings:

- **The production judge passes.** qwen3:8b clears the audit gate (recall ≥ 0.80, false alarm ≤ 0.20,
  decision flips ≤ 0.10) with zero decision flips and a trustworthy-verdict rate of 1.00. The
  "no defensible number" problem from `RESEARCH-2026-11-next-steps.md` §0 is closed for the
  judge itself: a faithful paraphrase no longer risks a 0.00 on the judge's account.
- **phi4-mini is not a viable second judge.** It has perfect recall but a 0.41 false-alarm rate
  (7 of 17 supported claims called unsupported) and 2 decision flips out of 16 probes. Using it
  as the second opinion would block releases that should ship. It is a smaller, less capable
  model and the result is consistent with that.
- **κ = 0.64 is moderate, not strong.** The two judges disagree on roughly a third of the
  supported/unsupported decisions. Agreement alone cannot distinguish "reliable" from "reliably
  wrong" (per *All Verdicts are Not Equal*); the trustworthy-verdict rate and the flip probe are
  what carry the validity claim. For a stronger cross-check, run with a larger second judge via
  Groq: `--judge2-backend groq --judge2-model llama-3.3-70b-versatile` (needs `GROQ_API_KEY`).
- **The gold set grew 26 → 35 items** during this pass, all from the shipped corpus docs
  (router, models, ollama, metrics, mcp, traces, faithfulness). It is still short of the 50
  recommended in the research; the remaining 15 should be adversarial near-misses (inverted
  length rules, swapped tiers, wrong counts) so the false-alarm cell keeps being exercised.

Consequence for the audit's priority order: §1.1's *code and machinery* work is done; the open
part is content (more labelled items) and a stronger second judge. §1.2 (a real v3 baseline) is
now the binding next step, because the judge it depends on is validated.
